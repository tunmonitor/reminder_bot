```markdown
# reminder_bot

Telegram-бот напоминаний по расписанию для Raspberry Pi.

## Возможности

- Групповые напоминания в чаты служений по настраиваемому расписанию.
- Персональные напоминания участникам с кнопкой подтверждения.
- Отдельные тексты и расписания для каждого пользователя.
- Предпросмотр группового напоминания с датой события и временем
  отправки, без фактической отправки сообщения.
- Пометки о событиях дня (причастие, праздник) в графике.
- Управление несколькими служениями, администраторами и привязками.
- Раздача Telegram Web App через отдельный HTTP-сервер.
- SQLite-реестр, аудит изменений, резервное копирование и
  восстановление.

## Установка

```bash
cd /home/pi/app/reminder_bot/prod      # или /mnt/external_data/reminder_bot/test
python3 -m venv venv                   # только если venv ещё не создан
./venv/bin/pip install -r requirements.txt
cp reminder_bot_credentials.env.example reminder_bot_credentials.env
# Заполнить BOT_TOKEN, ADMIN_TG_ID, GROUP_CHAT_ID, YANDEX_PUBLIC_URL.
cp webapp_config.example.json webapp_config.json
# При необходимости задать отдельный порт для этого окружения.
```

Зависимости устанавливаются в отдельное `venv/` каждого развёртывания.
На Raspberry Pi для работы из исходного репозитория используется
`/home/pi/.venv`. Скрипт `manage.sh` определяет `test` или `prod` по
имени каталога; команды запускаются из каталога развёртывания, не из
`src/`.

Совместимость: Python 3.10+, aiogram 3.x, APScheduler 3.x,
openpyxl 3.1+. Raspberry Pi OS (Bookworm, 64-bit).

## Управление

### Бот

```bash
./manage.sh start
./manage.sh status
./manage.sh restart
./manage.sh stop
```

`start` запускает бота. `stop` сохраняет текущий журнал взаимодействий
и останавливает бота. `restart` выполняет остановку и запуск. `status`
печатает `БОТ РАБОТАЕТ` или `БОТ ОСТАНОВЛЕН`.

### Web App

```bash
./manage.sh webapp start
./manage.sh webapp status
./manage.sh webapp restart
./manage.sh webapp stop
```

Web App — статическая страница в `webapp/`, раздаётся отдельным
HTTP-сервером. Параметры — в `webapp_config.json` (host, port,
public_url). Test и prod используют разные порты. Публичный доступ —
только через HTTPS reverse proxy.

### Логи, бэкапы, восстановление

```bash
./manage.sh logs
./manage.sh debug-logs
./manage.sh logs --follow
./manage.sh debug-logs --follow
./manage.sh backup
./manage.sh backup-data
./manage.sh restore-data /mnt/external_data/reminder_bot/backups/prod/<snapshot>
```

`backup` сохраняет interaction-лог. `backup-data` создаёт проверенный
снимок SQLite, SQL-экспорта, кэша, XLSX и JSON. Снимки хранятся в
`/mnt/external_data/reminder_bot/backups/{test|prod}/`. При отсутствии
внешнего диска операция завершается ошибкой.

Перед восстановлением остановите бота:

```bash
./manage.sh stop
./manage.sh restore-data /mnt/external_data/reminder_bot/backups/test/<snapshot>
./manage.sh start
```

`restore-data` проверяет окружение, manifest, контрольные суммы и
целостность SQLite. Восстановление из другого окружения запрещено.
При обнаружении SQLite -wal/-shm сначала разберитесь с их состоянием;
автоматическое удаление не выполняется.

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `SHM_BASE` | Корень оперативных каталогов | `/dev/shm/reminder_bot` |
| `SHM_DIR` | Каталог PID, xlsx, кэша | `$SHM_BASE/<env>` |
| `LOG_DIR` | Каталог логов | значение `SHM_DIR` |
| `REMINDER_BOT_DB_PATH` | Путь SQLite-реестра | `<project>/.runtime/reminder_bot.sqlite3` |
| `TIMEZONE` | Часовой пояс планировщика | `Europe/Moscow` |
| `NETWORK_WAIT_SECONDS` | Сколько `start` ждёт DNS для `api.telegram.org` | `300` |

Пример:

```bash
SHM_DIR=/dev/shm/reminder_bot/test LOG_DIR=/dev/shm/reminder_bot/test/logs ./manage.sh start
```

### Автозапуск после перезагрузки

После перезагрузки сервера DNS бывает недоступен несколько минут, хотя сеть
уже поднята. Поэтому `start` сначала ждёт, пока разрешится `api.telegram.org`
(до `NETWORK_WAIT_SECONDS`), а бот обновляет меню команд в фоне, уже после
записи PID-файла: `start` ждёт PID-файл не дольше 30 с и иначе завершает
процесс. Рекомендуемый crontab:

```cron
@reboot sleep 15 && /home/pi/app/reminder_bot/prod/manage.sh start
0 * * * * /home/pi/app/reminder_bot/prod/manage.sh start > /dev/null 2>&1
```

Ежечасный `start` ничего не делает, если бот уже работает.

## Команды бота

### Для администратора

- `/start` — главное меню: кнопки разделов, доступных роли.
- `/services` — список доступных служений.
- `/service_settings` — карточка служения: чат, напоминания, ближайшая
  отправка, администраторы и кнопки всех разделов служения.
- `/service_admin_add` — назначить администратора служения.
- `/service_admin_remove` — снять администратора.
- `/service_chat` — настроить или отключить групповой чат.
- `/service_contact` — обзор ответственных по датам (кто назначен и
  привязан ли Telegram) и изменение привязок.
- `/service_sync` — перечитать график и открыть тот же обзор.
- `/service_notify` — тексты и расписания напоминаний.
- `/test_notify` — проверка доставки.
- `/cancel` — прервать текущий диалог.

### Для пользователя

- `/my_schedule` — мои назначения из графика на ближайшие 6 недель.
- `/my_notifications` — личные уведомления: включение по служениям,
  напоминания от админа (только вкл./выкл.) и свои (до 10 на служение).
- `/cancel`, `/start`.

Команды работают только в личном чате с ботом. Служение выбирается
кнопкой. `/start` показывает кнопки разделов, доступных роли
пользователя. Меню команд Telegram тоже зависит от роли: участники
видят только `/start`, `/my_schedule`, `/my_notifications` и `/cancel`; меню
администратора обновляется при запуске бота, при `/start` и при
назначении или снятии администратора. Супер-администратор видит все служения, администратор — только
назначенные.

Списки служений во всех командах используют одинаковую сортировку и
компоновку: до восьми служений отображаются без пагинации (обычно
3+3+2); более длинные списки разбиваются на страницы, кнопки навигации
располагаются отдельным нижним рядом.

## Сценарии

### Первичная настройка служения (для супер-администратора)

1. `/services` — проверить список.
2. `/service_chat` → выбрать служение → выбрать группу, где бот уже
   состоит. Если в группе включены темы, админ служения отправляет
   `/here` в нужной теме (`/here sound`, если к чату привязано несколько
   служений) — напоминания и сообщения о подтверждениях пойдут туда.
   `/here` вне темы возвращает общую тему; при смене группы тема
   сбрасывается. Тема видна в карточке служения («🧵 Тема»); после
   `/here` бот подтверждает выбор в личном чате и присылает
   обновлённую карточку вместо прежней.
   Если участник нажал «🚫 Не смогу» в личном напоминании, бот
   сообщает админам и запускает в чате служения опрос «Кто сможет…»
   (12 часов, но не позже чем за 12 часов до дня события; если
   времени меньше — 1 час). По сроку замена — первый «Могу» из людей
   с этой задачей, иначе первый «Могу» остальных. Админ может
   назначить замену сам: `/change {задача} @username` (в личном чате
   или ответом на опрос). Замена действует на одну дату и главнее
   графика. Без отказа участника замену назначают «🔁 Замена» в
   карточке служения (дата → кого → задача → кто заменит) или
   `/change {задача} @username [дд.мм]`.
3. `/service_admin_add` → выбрать служение → выбрать пользователя или
   ввести `123456789 @username` → подтвердить.
4. `/service_contact` (или «👥 Ответственные» в `/start` и в карточке
   служения) → выбрать служение. Откроется обзор ближайшего события:
   задачи, назначенные люди и статус привязки (`✅ @username`,
   `✅ привязан`, `⚪ не привязан`), информационные пометки и счётчик
   «Привязано N из M». Кнопки `⬅️ дата` / `➡️ дата` листают события
   на 6 недель вперёд. «✏️ Изменить привязки» открывает состав
   служения: люди из «Списков», привязанные и люди графика
   (`⚠️ нет в списке` — есть в графике, но не в «Списках»). Человек →
   выбрать Telegram-пользователя: привязка действует сразу во всех его
   задачах. «➕ Добавить участника» — человек не из «Списков».
   На шаге выбора пользователя «⬅️ Назад» и `/cancel` возвращают к
   списку людей, не закрывая привязку. «🔔 Напоминания» открывает
   `/service_notify` этого служения. Telegram ID на экране не
   показываются.
5. `/service_notify` → выбрать служение:
   - откройте «Напоминания», добавьте напоминание и отдельно задайте
     его срок, время и при необходимости собственный текст;
   - «📌 Задача» в карточке — напоминание только для одной задачи
     (поля `{task}`, `{task_responsibles}`); если на дату у задачи
     никого нет, оно не отправляется, админ получает ⚠️;
   - у каждого напоминания свои текст и расписание (например,
     «анонс за 3 дня», «напоминание за 1 день», «финальное в день
     события»);
   - без собственного текста напоминание использует шаблон по
     умолчанию служения, а без него — встроенный шаблон;
   - «➕ Добавить напоминание» спрашивает срок, время и текст по
     шагам; запись создаётся после последнего шага;
   - при совпадении срока и времени бот предлагает объединить
     напоминания в одно сообщение и показывает, как оно будет
     выглядеть, либо сохранить отдельным сообщением;
   - «📋 Отчёт админам» — шаблон отчёта, который после группового
     напоминания приходит админам служения в личный чат (поля
     `{service_name}`, `{sunday_date}`, `{task_assignments}`,
     `{delivery_status}`, `{confirmation_status}`). Отчёт обновляется,
     когда участники нажимают «✅ Принял» или «🚫 Не смогу» в личном
     напоминании; после ответа личные напоминания на эту дату не
     повторяются;
   - изменения карточек групповых напоминаний сохраняются сразу.
     Общий шаблон, личные шаблоны и шаблон отчёта сохраняются кнопкой
     «Завершить и сохранить».
   - карточка показывает ближайшую дату отправки; предпросмотр отдельно
     отображает дату собрания и дату/время отправки, затем итоговый
     групповой текст. Предпросмотр не отправляет сообщение и предупреждает,
     если для события нет неинформационных задач.
     При нескольких параллельных запросах устаревший результат не
     заменяет экран последнего предпросмотра.
6. `/test_notify` → выбрать служение → проверить отправку.

Дата отправки группового напоминания — дата воскресного события минус
заданный срок. Карточка и предпросмотр выбирают ближайшее воскресенье,
для которого заданные дата и время отправки ещё не прошли; если время
сегодня уже прошло, показывается следующее подходящее воскресенье.

### Ежедневная поддержка

- После обновления графика — `/service_sync`: обзор сразу покажет,
  кто из новых ответственных ещё `⚪ не привязан`.
- При смене группы — `/service_chat`.
- Правка текстов — `/service_notify`.

### Участник смотрит свои служения

`/my_schedule` или «📅 Мои служения» в `/start` — назначения
пользователя на ближайшие 6 недель по датам. Информационные задачи и
чужие назначения не показываются. График читается с листов текущего и
следующих месяцев; отсутствующий будущий лист пропускается, повреждённый
лист приводит к сообщению об ошибке. Скачанный график кешируется на
5 минут и общий для всех пользователей.

### Пользователь настраивает личные уведомления

1. `/my_notifications` → выбрать служение (на `/start` бот подсказывает,
   в каких служениях личные напоминания выключены).
2. «🔔 Включить». Если напоминаний ещё нет, создаётся напоминание от
   админа «за 1 дн. в 18:00» для каждой задачи пользователя в служении.
3. Список напоминаний служения: 👤 — от админа (текст админа; можно
   только включить или выключить, либо «📋 Копировать как своё»),
   ✏️ — свои (своё время и текст, можно удалить).
4. «➕ Своё напоминание» → задача (если их несколько) → время (вариант
   или вручную, например `1 18:30`) → при желании «✏️ Изменить текст»
   (до 3000 символов). Своих напоминаний в служении — не больше 10.
   Два включённых напоминания одной задачи на одно время бот не
   сохраняет; копия создаётся выключенной — измените её время и
   включите.
5. Каждое личное напоминание начинается с заголовка «🔔 служение ·
   задача · дата служения», дальше — текст (свой или админа); к нему
   относятся кнопки «✅ Принял» / «🚫 Не смогу».

Уведомления включаются, только если хотя бы одно включённое правило
относится к задаче пользователя в текущем графике. Правила задач, которых
в графике уже нет, не учитываются; задачам без правил назначается правило
по умолчанию, выключенные правила автоматически не включаются. Иначе
служение остаётся выключенным, и бот сообщает причину: график не
загрузился, в графике нет задач пользователя или все правила выключены.
Так не бывает состояния «включено, но ничего не придёт». При смене времени существующее правило обновляется
на месте, а отметки об уже отправленных напоминаниях сохраняются.

Личные уведомления выключены по умолчанию для каждого служения.
Пользователь может включить их сам. Групповые уведомления работают
независимо и не зависят от личных настроек.

### Каталог служений и задач

Служения, их задачи и колонки месячного листа заданы в
`reminder_bot_services.json`. Суперадмин может включать, выключать и
добавлять задачи в карточке служения → «📋 Задачи служения»; эти
правки хранятся в SQLite и файлом не перезаписываются. Выключенные
задачи (сейчас «кофе» и «спевка») не читаются из графика. Задача из
графика, которой нет в каталоге, пропускается, а администратор
получает предупреждение «задача не из списка». Подробности — tz2.txt,
раздел 2.1.1.

### Информационные задачи в графике

Задачи-пометки о событиях дня помечаются в Excel префиксом `*` или
обрамлением `[...]`:

```
* Причастие (В.П.)
[Праздник]
```

Такие задачи:

- не предлагаются для привязки ответственных;
- не учитываются в счётчике «Привязано N из M»;
- не порождают личных уведомлений;
- остаются видимыми в `/service_notify` с пометкой «инфо».

## Разработка

1. Разработка в ветке `dev` в `/home/pi/app/reminder_bot/src`.
2. PR `dev → test`: unit-тесты на GitHub-hosted runner, затем деплой
   в `/mnt/external_data/reminder_bot/test` self-hosted runner'ом.
3. Тестовый бот остаётся запущенным для ручной проверки.
4. После одобрения — PR `dev → main`. После merge в `main` workflow
   синхронизирует проект в `/home/pi/app/reminder_bot/prod`.

Подробности — в `.github/workflows/deploy.yml` и разделе 7 `zt.txt`.

### Тесты локально

```bash
cd /home/pi/app/reminder_bot/src
mkdir -p /dev/shm/app/reminder_bot/src/.tmp
TMPDIR=/dev/shm/app/reminder_bot/src/.tmp \
    /home/pi/.venv/bin/python -m unittest discover -s tests -v

После завершения удалить только созданные тестовые файлы, не

### Отладка парсинга Excel

```bash
/home/pi/.venv/bin/python -m bot.debug_schedule
/home/pi/.venv/bin/python -m bot.debug_schedule --date 2026-10-11
```

Файл и debug-лог сохраняются в `/dev/shm/reminder_bot/debug/`. Сообщения
не отправляются. Удаляйте сохранённые файлы вручную после отладки.

### Проверка целостности SQLite

```bash
python - <<'PY'
import sqlite3
from pathlib import Path
path = Path('.runtime/reminder_bot.sqlite3')
if not path.exists():
    raise SystemExit('SQLite-файл не найден: ' + str(path))
with sqlite3.connect(path) as conn:
    print(conn.execute('PRAGMA integrity_check;').fetchone()[0])
PY
```

Ожидаемый результат: `ok`.

## Безопасность

- `--shm-dir` и `--log-dir` принадлежат пользователю бота, не содержат
  символических ссылок в компонентах пути, недоступны группе и другим.
- Каталоги 700, файлы логов и бэкапов 600, PID-файл создаётся атомарно
  и удаляется владельцем.
- Debug-лог содержит Telegram ID и тексты сообщений — не публиковать.
- Runtime-логи не выгружаются в GitHub artifacts.
- Секреты хранятся только в `credentials.env`, `webapp_config.json`
  и папках развёртывания, исключены из Git.

## Ограничения текущей версии

- Для служений, кроме «Собрания», расписание и настройки сохраняются,
  но плановая отправка подключена частично.
- Web App раздаёт статику; API для чтения/изменения данных бота
  пока не предоставляется.
- Восстановление данных выполняется только при остановленном боте.
