
🗂️ 1. Где размещать файлы?

Лучше всего размещать файлы EXECUTION_PLAN.md и BACKLOG.md прямо в корне проекта.
• Для Codex корень репозитория — это «точка отсчета». Когда файлы лежат в корне, агенту гораздо проще индексировать их и сопоставлять со структурой папок bot/, src/ и т.д.
• Файл QUESTIONS_FOR_CUSTOMER.md (уже с ответами заказчика) можно временно положить туда же. После того как Codex перенесет задачи из него в план разработки, этот файл ответов можно будет удалить или переместить в архивную папку (например, .codex/history/).

🤖 2. Фаза 1: Актуализация плана (Промпт для Codex)

Когда вы зальете файлы в корень и откроете чат Codex в VS Code (или Copilot Edits), ваш первый промпт должен выглядеть так:
«Изучи структуру проекта, а также файлы EXECUTION_PLAN.md, BACKLOG.md и ответы заказчика в QUESTIONS_FOR_CUSTOMER.md. На основе ответов заказчика перенеси соответствующие задачи из бэклога и вопросов в EXECUTION_PLAN.md, сформулировав их как четкие технические требования. Обнови BACKLOG.md. Выведи мне измененный текст EXECUTION_PLAN.md для согласования».

🛠️ 3. Фаза 2: Запуск автономной разработки (Промпт для Codex)

После того как вы утвердили обновленный EXECUTION_PLAN.md, вы даете Codex команду на выполнение. Ваш промпт полностью совпадает с тем, что вы описали:
«Возьми в работу актуальный EXECUTION_PLAN.md. Создай локальную ветку dev (или переключись на нее). Поэтапно выполняй задачи: пиши код, запускай существующие тесты с помощью pytest (или вашей команды тестирования). При обнаружении ошибок — исправляй их на месте (self-healing). После того как все тесты станут зелеными, сделай коммит, отправь ветку в GitHub и создай Pull Request из dev в test».

🔄 4. Цикл проверки на GitHub (CI/CD + Агент)

То, что вы описали дальше — это вершина автоматизации:
1. GitHub Actions запускает тесты в облаке.
2. Подключенный к GitHub агент (например, через GitHub Copilot для PR или OpenAI Symphony) анализирует логи сборки.
3. Если CI упал, агент оставляет инлайн-комментарии (Review Comments) прямо в коде Pull Request.
4. Codex в VS Code (через интеграцию с GitHub) видит эти комментарии, автоматически подтягивает их как новые задачи, исправляет код локально, делает новый коммит в ветку dev, и GitHub Actions перезапускается. Цикл повторяется до полного успеха.

⚠️ Важные чек-листы перед стартом:

• База данных: Убедитесь, что у Codex локально есть доступ к тестовой базе данных (или настроены mock-тесты), иначе команда запуска тестов упадет просто из-за отсутствия подключения к БД.
• Доступы (Tokens): У Codex в VS Code должны быть права на запись в ваш репозиторий GitHub (Write permissions), чтобы он мог сам пушить ветки и создавать PR.
Схема полностью рабочая и готова к запуску.
