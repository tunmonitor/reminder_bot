ТЗ для ИИ-агента на разработку кода Telegram-бота. 

ДЕТАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)
Проект: Telegram-бот напоминаний по расписанию (reminder_bot.py)
Целевая платформа: Raspberry Pi (ОС Linux)
Язык и стек: Python 3.10+, aiogram 3.x (асинхронный), openpyxl или pandas, APScheduler, aiohttp.

1. АРХИТЕКТУРА И ИНФРАСТРУКТУРА ХРАНЕНИЯ ДАННЫХ
В целях минимизации износа SD-карты на Raspberry Pi и обеспечения безопасности данных, проект использует строгое трехуровневое разделение памяти и файловой структуры.

1.1. Локальная структура папок на жестком диске (SD-карта)
Бот разворачивается в трех изолированных директориях в зависимости от окружения:

/home/pi/app/reminder_bot/src — директория исходного Git-проекта, привязанная к репозиторию https://github.com/tunmonitor/reminder_bot. Здесь запускается self-hosted GitHub Runner.

/mnt/external_data/reminder_bot/test — изолированная папка тестового окружения (создается символическая ссылка на /home/pi/app/reminder_bot/test).

/home/pi/app/reminder_bot/prod — директория боевой (Production) версии бота.

1.2. Статические файлы настроек (хранятся на SD-карте в папках test и prod):
Эти файлы исключены из Git через .gitignore и настраиваются на сервере вручную:

credentials.env — конфиденциальные токены и ID.
templates.json — шаблоны текстов уведомлений для кастомизации.
schedule_config.json — расписание запусков планировщика.
logs_backup/ — папка для персистентного хранения ежедневных бэкапов логов.

1.3. Оперативные данные и логи (RAM-диск /dev/shm):
Все динамические операции производятся в оперативной памяти. Чтобы тестовая и боевая версии бота не конфликтовали, пути в ОЗУ разделяются динамически на основе пути запуска скрипта:

Путь для теста: /dev/shm/reminder_bot/test/
Путь для продакшна: /dev/shm/reminder_bot/prod/

Пути к оперативной директории и директории логов НЕ зашиты в код, а передаются боту снаружи — через аргументы командной строки --shm-dir <path> и --log-dir <path> (см. раздел 6.1). Это позволяет:
- запускать test- и prod-экземпляры одновременно, не пересекаясь по файлам;
- в отладке перенаправлять данные в произвольный каталог (например, --shm-dir /tmp/rb_debug).

Внутри ОЗУ-директории, переданной через --shm-dir, создаются файлы:
- reminder_bot_bot.pid — файл с PID-процессом текущего запущенного экземпляра.
- reminder_bot_current.xlsx — актуальный файл расписания, скачанный с Яндекс.Диска.
- reminder_state_cache.json — кэш текущей недели с ID назначенных пользователей и статусами их подтверждений.

В директории, переданной через --log-dir (по умолчанию совпадает с --shm-dir), создаются:
- reminder_bot_interaction.log — файл логов действий пользователей (INFO).
- reminder_bot_debug.log — файл глубокой отладки систем и интеграций (DEBUG).

2. МОДЕЛЬ ДАННЫХ И ЛОГИКА ПАРСИНГА EXCEL
(расширение описание смотри в файле tz2.txt)
Бот скачивает Excel-файл по прямой ссылке с Яндекс.Диска перед каждым сеансом рассылки.

2.1. Алгоритм определения даты:
Бот вычисляет дату ближайшего предстоящего воскресенья относительно текущего момента времени с учетом целевого часового пояса (из credentials.env, по умолчанию Europe/Moscow).

Формула: Текущая дата + (6 - Текущий день недели) дней. Если сегодня воскресенье — вычисляется следующее воскресенье (+7 дней).
Дата переводится в формат ДД.ММ.ГГГГ (например, 04.11.2026). Сравнение дат должно происходить на уровне объектов datetime.date, а не строк, во избежание сбоев на стыке месяцев/лет.

2.2. Лист месячного расписания:
Имя листа строится по месяцу и двум последним цифрам года: например,
ОКТЯБРЬ26, НОЯБРЬ26. Регистр имени листа не имеет значения. В первой строке
может быть название служения (например, СОБРАНИЕ). Строки даты находятся
отдельно в колонке A; дата может быть Excel-датой или текстом «4 октября».
Задачи и назначенные люди находятся в колонках A и B соответственно. Все
строки после даты до следующей даты принадлежат одному блоку; пустые строки
блок не завершают.

Задачи сопоставляются без учёта регистра: ХКЦ → Ответственный,
Ведущий/Ведет → Ведущий, Проповедует/Проповедет → Проповедник. Для целевой
даты обязательны все три назначения.

2.3. Лист «Списки»:
Заголовок задачи находится в колонке A и может встречаться в любой строке,
не только в A1. В последующих строках блока имя находится в A, Telegram
username — в B, Telegram_ID — в C. Следующий заголовок начинает новый блок;
пустые и частично заполненные строки разрешены. Неизвестный заголовок задачи,
выделенный жирным, также начинает новый блок, но его участники не используются.
Имя из расписания ищется в блоке соответствующей задачи. Для назначенного
человека обязателен положительный целый Telegram_ID; username необязателен и
возвращается без @.

2.4. Ошибки и неполные данные:
Если невозможно скачать/прочитать книгу, не найден месячный лист или дата,
ошибка записывается в debug-лог и администратору отправляется сообщение
в Telegram. Если не найдено назначение для отдельной роли, имя отсутствует
в соответствующем блоке «Списки» или не указан корректный Telegram_ID,
бот уведомляет администратора, но продолжает частичную рассылку:
- групповое сообщение отправляется после разбора доступных данных;
- для отсутствующего group username указывается «не найден»/«не указан»;
- личные сообщения с кнопкой подтверждения получают только люди с
  сопоставленным положительным Telegram_ID;
- state cache содержит только фактически сопоставленные назначения.

В debug-лог записываются прочитанные назначения, результаты сопоставления,
причины отсутствующих данных и итоговые тексты группового и личных сообщений.
Не публикуйте логи: они могут содержать Telegram ID и личные данные.

Для безопасной проверки без отправки сообщений используйте:
`/home/pi/.venv/bin/python -m bot.debug_schedule --date YYYY-MM-DD`.
Команда сохраняет xlsx и логи в `/dev/shm/reminder_bot/debug/`, где они не
удаляются автоматически; права каталога 700, файлов 600.

3. СИСТЕМА ЛОГИРОВАНИЯ И АУДИТА
В коде настраиваются два независимых логгера через стандартный модуль logging:

Логгер взаимодействий (reminder_bot_interaction.log):
Уровень: INFO. Место: директория, переданная через --log-dir (по умолчанию — ОЗУ-директория --shm-dir).
Что фиксирует: Успешный старт рассылки, отправку сообщений в группу, а также факт нажатия пользователями кнопок подтверждения с указанием их ID, Username и роли.

Логгер отладки (reminder_bot_debug.log):
Уровень: DEBUG. Место: директория, переданная через --log-dir.
Что фиксирует: запросы к API Яндекс.Диска (HTTP-статусы), размеры скачиваемых файлов, распознанный лист/назначения, сопоставленные Telegram-данные и подготовленные тексты сообщений. При сбоях записываются диагностические ошибки и stack trace. Лог содержит персональные данные и не должен публиковаться.

4. БИЗНЕС-ЛОГИКА УВЕДОМЛЕНИЙ И ОБРАТНАЯ СВЯЗЬ
Бот активируется планировщиком APScheduler по дням недели и времени из reminder_bot_schedule_config.json (например: среда 09:00, пятница 18:00). При срабатывании триггера запускается веерная рассылка:

Общее уведомление: После успешного разбора книги отправляется одно сообщение в групповой чат (GROUP_CHAT_ID) по шаблону general из reminder_bot_templates.json. Для роли без сопоставленного username используется пометка «не найден»/«не указан».
Персональные уведомления в ЛС: Личное сообщение по шаблону роли отправляется каждому найденному назначенному участнику, для которого есть положительный Telegram_ID. Отсутствие данных отдельной роли не блокирует сообщения остальным.
Ошибки отдельных назначений: Администратор получает сообщение с датой и описанием отсутствующих данных. Общая рассылка и доступные личные сообщения продолжаются. Ошибки скачивания, чтения книги или поиска целевого листа/даты препятствуют рассылке и сообщаются администратору.
Ограничение частоты (Rate Limiting): Для предотвращения ошибок HTTP 429 (Too Many Requests) между отправками сообщений в цикле строго закладывается пауза await asyncio.sleep(0.05).
Интерактивная кнопка подтверждения:
Под каждым ЛС-сообщением крепится инлайн-кнопка «Принял, буду», кодирующая в callback_data дату и роль.
Защита от двойного клика (Идемпотентность): При нажатии бот проверяет статус в state_cache.json. Если флаг confirmed уже равен true, пользователю выдается answer_callback_query с текстом «Вы уже подтвердили участие!».
Если клик первый: флаг меняется на true, сообщение в ЛС изменяется (добавляется галочка ✅), а в общий групповой чат отправляется апдейт: "🔔 Участник Аркадий подтвердил роль Ответственного".

5. БЕЗОПАСНОСТЬ И УСТОЙЧИВОСТЬ К СБОЯМ

Стратегия повторных попыток (Retry Policy): При скачивании расписания с Яндекс.Диска, в случае сетевого сбоя или таймаута, бот совершает до 3 попыток запроса с интервалом в 5 минут. Если все попытки провалены — шлется алерт Администратору и рассылка не выполняется.
Часовой пояс: Принудительное использование таймзоны (из конфига) во всех операциях сравнения дат и внутри планировщика.
Самоочистка кэша: В ОЗУ хранятся данные только текущей недели. При парсинге новой даты старый кэш затирается.
Мягкое завершение (Graceful Shutdown): Python-скрипт перехватывает сигналы SIGTERM и SIGINT (через модуль signal), корректно закрывает сессии aiohttp и aiogram, а также удаляет собственный reminder_bot_bot.pid (в директории --shm-dir) перед выходом.

6. УПРАВЛЕНИЕ СКРИПТОМ (reminder_bot_manage.sh) И АВТОЗАПУСК (cron)
В корне проекта лежит Bash-скрипт reminder_bot_manage.sh. Он принимает аргументы start, stop, restart, status, backup, logs, debug-logs, clear-logs и автоматически определяет окружение (test или prod) по имени каталога, в котором он лежит.

start: проверяет reminder_bot_bot.pid в ОЗУ. Если процесс не запущен — активирует venv, восстанавливает reminder_bot_interaction.log из последнего бэкапа (если ОЗУ чистая), запускает бота в фоне через nohup python3 -u reminder_bot.py --shm-dir ... --log-dir ... &, сохраняет PID + starttime в PID-файл. Если процесс уже работает — выход с кодом 1 без повторного запуска (идемпотентность для cron).

stop: считывает PID, делает backup, мягко тушит процесс через kill -15, при необходимости — kill -9, удаляет PID-файл. Дополнительно находит и останавливает legacy-процессы reminder_bot.py, запущенные без PID-файла.

restart: выполняет stop, затем start. Используется CI/CD-пайплайном (раздел 7).

status: печатает БОТ РАБОТАЕТ / БОТ ОСТАНОВЛЕН (первая строка stdout) — формат, на который опирается CI-проверка в разделе 7.

backup: копирует актуальный reminder_bot_interaction.log из ОЗУ на жёсткий диск в папку logs_backup/ с добавлением текущей даты в имя файла (reminder_bot_interaction_YYYY-MM-DD.log), исключая потерю истории при перезагрузках Pi.

logs / debug-logs / clear-logs: просмотр и очистка reminder_bot_interaction.log, reminder_bot_debug.log, sys_nohup.log.

6.1. Передаваемые боту аргументы.
reminder_bot_manage.sh при каждом запуске передаёт reminder_bot.py следующие CLI-аргументы:

┌─────────────────────┬────────────┬──────────────────────────────────┬──────────────────────────────────────────────────────────┐
│ Аргумент            │ Обязателен │ Значение по умолчанию            │ Назначение                                               │
├─────────────────────┼────────────┼──────────────────────────────────┼──────────────────────────────────────────────────────────┤
│ --shm-dir <path>    │ да         │ /dev/shm/reminder_bot/<env>      │ Директория оперативных данных (PID, xlsx, state_cache)   │
│ --log-dir <path>    │ да         │ равно --shm-dir                  │ Директория логов (interaction.log, debug.log)            │
└─────────────────────┴────────────┴──────────────────────────────────┴──────────────────────────────────────────────────────────┘

Оба пути можно переопределить через переменные окружения SHM_DIR и LOG_DIR перед вызовом reminder_bot_manage.sh:

SHM_DIR=/dev/shm/reminder_bot/prod LOG_DIR=/var/log/reminder_bot ./reminder_bot_manage.sh start

Значения <env> определяется автоматически как имя каталога, в котором лежит reminder_bot_manage.sh: test или prod.

6.2. Контракт с reminder_bot.py.
Скрипт reminder_bot.py обязан:
1. Разбирать аргументы через argparse с ключами --shm-dir и --log-dir.
2. Использовать --shm-dir для размещения reminder_bot_bot.pid, reminder_bot_current.xlsx, reminder_state_cache.json.
3. Использовать --log-dir для размещения reminder_bot_interaction.log и reminder_bot_debug.log.
4. Создавать обе директории при старте (os.makedirs(..., exist_ok=True)).
5. Удалять reminder_bot_bot.pid при graceful shutdown (см. раздел 5).

6.3. Спецификация для crontab -e пользователя pi:

@reboot        /home/pi/app/reminder_bot/prod/reminder_bot_manage.sh start
0 * * * *      /home/pi/app/reminder_bot/prod/reminder_bot_manage.sh start > /dev/null 2>&1
30 23 * * *    /home/pi/app/reminder_bot/prod/reminder_bot_manage.sh backup > /dev/null 2>&1

7. СЦЕНАРИЙ CI/CD ПАЙПЛАЙНА (GIT FLOW ПОД ЛОКАЛЬНЫЕ ПУТИ)
Автоматический деплой описывается в `.github/workflows/deploy.yml`.
Процесс разработки и выпуска:

1. Изменения делаются и коммитятся в ветку `dev` в исходной папке
   `/home/pi/app/reminder_bot/src`.
2. PR `dev -> test` запускает unit-тесты на GitHub-hosted runner. После их
   успешного завершения self-hosted runner с меткой `tunmonitor` получает
   проверяемый commit ветки `dev`, останавливает тестовый бот и синхронизирует
   проект в `/mnt/external_data/reminder_bot/test`. Это тестовая копия исходного
   проекта; сам бот запускается из папки `test` с отдельным каталогом данных
   `/dev/shm/reminder_bot/test`.
3. Тестовый бот остаётся запущенным для ручной проверки. Если обнаружены ошибки,
   исправления коммитятся в `dev`; обновление PR повторно проходит unit-тесты и
   разворачивается в тестовой папке. Переход к production выполняется после
   успешной ручной проверки и одобрения кода.
4. После одобрения создаётся/сливается PR `dev -> main`. PR запускает unit-тесты,
   но не изменяет production. После merge в `main` workflow синхронизирует
   отслеживаемые файлы проекта в `/home/pi/app/reminder_bot/prod` и запускает
   отдельный рабочий экземпляр бота из папки `prod` с данными в
   `/dev/shm/reminder_bot/prod`.

При синхронизации обновляется весь отслеживаемый код из соответствующего
проверенного commit. Локальные credentials, шаблоны, конфигурация расписания,
виртуальное окружение и резервные копии логов сохраняются в папках окружений.
Зависимости устанавливаются из `requirements.txt` в Python-среду, выбранную
`manage.sh`. Runtime-логи содержат личные данные: workflow не загружает их в
GitHub artifacts и не выводит их содержимое в Actions log.

  }
}
