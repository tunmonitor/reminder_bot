ДЕТАЛЬНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)
Проект: Telegram-бот напоминаний по расписанию (reminder_bot)
Целевая платформа: Raspberry Pi (ОС Linux)
Язык и стек: Python 3.10+, aiogram 3.x, openpyxl, APScheduler, aiohttp, SQLite
Дополнения: формат Excel, визуализация диалогов, резервное копирование и
Telegram Web App описаны в файле tz2.txt.


1. АРХИТЕКТУРА И ИНФРАСТРУКТУРА ХРАНЕНИЯ ДАННЫХ

Проект использует строгое разделение исходников, постоянных данных и
оперативных данных. Постоянные данные и резервные копии хранятся вне
/dev/shm.

1.1. Локальная структура папок

/home/pi/app/reminder_bot/src — исходный Git-проект, привязанный к
репозиторию https://github.com/tunmonitor/reminder_bot. Здесь запускается
self-hosted GitHub Runner.

/home/pi/app/reminder_bot/src/webapp/ — исходники Telegram Web App.
Сейчас содержит index.html как точку входа; развивается до полноценного
интерфейса Mini App. Каталог включается в развёртывания test и prod без
пользовательских секретов.

/mnt/external_data/reminder_bot/test — изолированная папка тестового
окружения. Создаётся символическая ссылка /home/pi/app/reminder_bot/test
на эту директорию.

/home/pi/app/reminder_bot/prod — директория боевой (Production) версии
бота.

1.2. Статические файлы настроек (в папках test и prod)

Файлы исключены из Git через .gitignore и настраиваются вручную:

credentials.env — токены, ID, часовой пояс, ссылка на Яндекс.Диск.
templates.json — шаблоны текстов уведомлений.
schedule_config.json — legacy-расписание (используется только при
недоступном SQLite-реестре).
webapp_config.json — адрес привязки и порт HTTP-сервера Web App.
logs_backup/ — персистентные бэкапы журналов взаимодействий.

1.3. Оперативные данные (RAM-диск /dev/shm)

Пути к оперативной директории и директории логов передаются боту снаружи
через аргументы --shm-dir и --log-dir (раздел 6.1). Это позволяет
запускать test и prod одновременно, не пересекаясь по файлам.

Путь для теста: /dev/shm/reminder_bot/test/
Путь для продакшна: /dev/shm/reminder_bot/prod/

Внутри --shm-dir создаются:
- reminder_bot_bot.pid — PID текущего экземпляра.
- reminder_bot_current.xlsx — актуальный файл расписания с Яндекс.Диска.
- reminder_state_cache.json — кэш текущей недели.
- reminder_bot_webapp.pid — PID HTTP-сервера Web App.

В --log-dir (по умолчанию совпадает с --shm-dir) создаются:
- reminder_bot_interaction.log — лог действий пользователей (INFO).
- reminder_bot_debug.log — технический лог (DEBUG).
- reminder_bot_webapp.log — журнал HTTP-сервера.
- sys_nohup.log — stdout/stderr процесса бота.

Правила размещения временных файлов:
- Временные файлы runtime-приложения — только в каталогах --shm-dir /
  --log-dir.
- Отладочные артефакты локальных тестов — в
  /dev/shm/app/reminder_bot/src/.tmp (TMPDIR для тестов).
- Запрещено использовать /tmp, /var/tmp, домашний каталог или SD-карту
  для временных данных.

1.4. Python-окружения

При работе из исходного репозитория /home/pi/app/reminder_bot/src
используется общее окружение /home/pi/.venv. Команды запускаются через
/home/pi/.venv/bin/python или /home/pi/.venv/bin/pip.

Развёрнутые экземпляры test и prod имеют собственный venv/ в своих
каталогах. Не копировать /home/pi/.venv и не переключать работающий бот
на окружение исходного репозитория.

1.5. Хранилище SQLite-реестра

Постоянная конфигурация служений, привязок, пользовательских уведомлений
и аудита хранится в SQLite. По умолчанию база создаётся в
.runtime/reminder_bot.sqlite3 внутри проекта. Путь можно переопределить
переменной REMINDER_BOT_DB_PATH в credentials или окружении.

Права: файл 600, каталог 700. Относительный путь считается от корня
проекта. Схема БД описана в разделе 4 tz2.txt.

1.6. Постоянные резервные копии

Единственное место хранения — смонтированный внешний диск:

    /mnt/external_data/reminder_bot/backups/{test|prod}/

Подкаталоги test и prod изолированы. При недоступном диске резервное
копирование не выполняется, ошибка логируется, администратор получает
уведомление. Основной бот продолжает работу.

Структура снимка, моменты создания, атомарная публикация и восстановление
описаны в разделе 4 tz2.txt.

1.7. Telegram Web App

Web App — статическая страница и ресурсы в webapp/. Раздаётся отдельным
HTTP-сервисом, управляется отдельно от бота:

    ./manage.sh webapp start|stop|restart|status

Параметры сервиса — host и port — задаются в webapp_config.json каждого
окружения. Test и prod используют независимые порты. По умолчанию
сервис слушает loopback и публикуется наружу через HTTPS reverse proxy.

Правила валидации initData и требования безопасности — в разделе 5
tz2.txt. Публичный HTTPS обязателен. Секреты и токены не попадают в
клиентские файлы и логи.


2. МОДЕЛЬ ДАННЫХ И ПАРСИНГ EXCEL

Бот скачивает Excel-файл по прямой ссылке с Яндекс.Диска перед каждым
сеансом рассылки. Подробности формата — раздел 2 tz2.txt.

2.1. Алгоритм определения даты

Бот вычисляет дату ближайшего предстоящего воскресенья с учётом часового
пояса из credentials (по умолчанию Europe/Moscow).

Формула: Текущая дата + (6 − день недели) дней. Если сегодня
воскресенье — следующее воскресенье (+7 дней). Сравнение дат выполняется
на уровне объектов datetime.date.

2.2. Лист месячного расписания

Имя листа — русское название месяца и две цифры года: ОКТЯБРЬ26,
НОЯБРЬ26. Регистр не важен. Первая строка может содержать название
служения. Строки дат в колонке A открывают блоки. Дата — Excel-дата или
текст «4 октября» / «4 октября 2026» / ДД.ММ.ГГГГ. Задачи и имена — в
колонках A и B. Пустая строка блок не закрывает; блок заканчивается
только при встрече следующей даты.

Распознаваемые задачи (регистр не важен):
- ХКЦ / Ответственный → Ответственный
- Ведущий / Ведет → Ведущий
- Проповедует / Проповедет / Проповедник → Проповедник

Информационные задачи (пометки о дне служения, а не назначения) не
обрабатываются как задачи для конкретного человека. Правила пометки —
раздел 2.5 tz2.txt.

2.3. Лист «Списки»

Заголовок задачи в A, может встречаться на любой строке. В строках
участников: A — имя, B — username, C — Telegram ID. Следующий заголовок
начинает новый блок. Пустые и частично заполненные строки разрешены.
Для участника обязателен положительный целый Telegram ID; username
необязателен и возвращается без @.

2.4. Ошибки и неполные данные

Ошибки скачивания/чтения/поиска листа или даты — администратор
уведомляется, рассылка не выполняется.

Ошибки данных по отдельным ролям (нет назначения, имя не найдено, нет
Telegram ID) — администратор уведомляется, рассылка продолжается:
- групповое сообщение отправляется после разбора доступных данных;
- известный username показывается в группе без @; для отсутствующего —
  «не найден»;
- личные сообщения получают только участники с корректным Telegram ID;
- state cache хранит назначения, включая неразрешённые;
- при следующем запуске повторяются только неудавшиеся доставки;
  исправление расписания обновляет групповое сообщение и добавляет
  недостающие личные.

2.5. Информационные задачи

Пометки о событиях дня (причастие, праздник, благодарения, членское
собрание) помечаются в Excel префиксом `*` или обрамлением `[...]`:

    * Причастие (В.П.)
    [Праздник]

Парсер:
- отсекает префикс, хранит чистое имя;
- проставляет флаг is_informational=True;
- такие задачи не показываются в списке для привязки ответственных;
- не учитываются в счётчике «Привязано N из M»;
- не порождают личных уведомлений;
- не входят в проверку «все привязаны»;
- в админском /service_notify остаются видимыми с пометкой «инфо».

Флаг is_informational не хранится в БД — производное от Excel, вычисляется
при каждом парсинге. Правила пометки и граничные случаи — раздел 2.5
tz2.txt.


3. СИСТЕМА ЛОГИРОВАНИЯ И АУДИТА

Два независимых логгера через стандартный модуль logging.

3.1. Логгер взаимодействий (reminder_bot_interaction.log)

Уровень INFO. Место — директория --log-dir.
Фиксирует: старт рассылки, отправку сообщений в группу, факт нажатия
кнопок подтверждения с указанием ID, username и роли.

3.2. Логгер отладки (reminder_bot_debug.log)

Уровень DEBUG. Место — директория --log-dir.
Фиксирует: запросы к Яндекс.Диску, размеры скачиваемых файлов,
распознанный лист и назначения, сопоставленные Telegram-данные,
подготовленные тексты сообщений, стек-трейсы исключений, детали работы
планировщика, фильтрацию информационных задач.

Логи содержат персональные данные (Telegram ID, username, имена). Не
публиковать. Права файлов 600, каталога 700.

3.3. Аудит изменений

SQLite-таблица configuration_audit хранит все изменения конфигурации:
кто (actor_id), что (action), когда (created_at) и что именно
(details_json). Просмотр — только супер-администратором через SQLite.


4. БИЗНЕС-ЛОГИКА УВЕДОМЛЕНИЙ И ОБРАТНАЯ СВЯЗЬ

Модель групповых и персональных напоминаний симметрична: напоминание —
это единая сущность «текст + расписание». Ни текст, ни расписание не
настраиваются отдельно друг от друга; вместе они образуют одно
напоминание, которое можно редактировать, включать, выключать и
удалять как единое целое.

4.1. Групповые напоминания

Каждое групповое напоминание — отдельная запись group_reminders со
следующими полями:
- service_id — к какому служению относится;
- body — текст напоминания (может быть NULL);
- reminder_days — за сколько дней до события отправлять;
- reminder_time — локальное время отправки ЧЧ:ММ;
- enabled — включено/выключено.

Если body = NULL, используется services.group_template — общий шаблон
служения. Если и он не задан, применяется встроенный шаблон по
умолчанию. Это позволяет администратору:
- задать общий текст один раз и использовать его в нескольких
  напоминаниях;
- оставить body = NULL у всех напоминаний и использовать общий
  шаблон для каждого;
- для конкретного напоминания задать собственный текст;
- вернуть напоминание к общему шаблону, сбросив body в NULL.

Расписаний у одного служения может быть несколько. Каждое — со своим
сроком и временем. Например, для «Собрания»:
- напоминание «Анонс»: за 3 дня в 18:00, свой текст;
- напоминание «Детали»: за 1 день в 09:00, свой текст;
- напоминание «Финальное»: в день события в 07:00, шаблон по умолчанию.

Каждое напоминание имеет устойчивый id и не зависит от других.
Изменение одного не затрагивает остальные. Удаление напоминания
удаляет только его.

Успех отправки фиксируется в group_reminder_deliveries по ключу
(reminder_id, event_date, recipient_key). Повторный запуск
планировщика повторяет только неуспешные доставки.

Таблица service_reminders сохраняется для возможности отката, но
штатная отправка и UI используют только group_reminders. Одноразовая
транзакционная миграция переносит расписания и историю доставок;
маркер в group_reminder_migrations обеспечивает идемпотентность при
повторной инициализации. Старые задания service-reminder-* удаляются
при старте до регистрации новых group-reminder-*.

4.2. Персональные уведомления

Две независимые ветки:

A. Административная — сервисная рассылка по контактам
   responsible_contacts. Работает как раньше.

B. Персональная — пользовательские уведомления по правилам
   user_reminder_texts + user_reminder_schedules.
   Модель: текст первичен, расписание — свойство текста, может быть
   несколько. Пользователь сам включает/выключает уведомления и
   настраивает расписания через /my_notifications.

Приоритет текста (resolve_text_for_user):
1. Если user_reminder_texts.body задан — использовать его.
2. Иначе service.personal_templates[task].
3. Иначе DEFAULT_TEMPLATE.

Условия отправки персонального уведомления:
- user_notification_prefs.enabled = True;
- schedule.enabled = True;
- service.enabled = True;
- задача не помечена информационной;
- пользователь присутствует в responsible_contacts для этой задачи;
- уведомление ещё не доставлено по (schedule_id, event_date).

Групповые напоминания и персональные независимы. Существующие
services.group_template и services.personal_templates не изменяются
персональной веткой. group_reminders не влияют на персональные
расписания и наоборот.

4.3. Обратная связь

Под личным сообщением крепится инлайн-кнопка «Принял, буду» с датой
и ролью/задачей в callback_data.

Поведение:
- первое нажатие: флаг confirmed = True, сообщение редактируется
  (добавляется ✅), в группу уходит апдейт
  «🔔 Участник ... подтвердил ...»;
- повторное нажатие: подтверждение сохраняется, апдейт отправляется
  только если раньше не доставлен;
- ошибка группового апдейта не отменяет подтверждение и оставляет
  кнопку для повтора.

4.4. Rate limiting

Между отправками в цикле — пауза await asyncio.sleep(0.05) для защиты
от HTTP 429.

4.5. Планировщик

APScheduler использует CronTrigger с временем из каждого напоминания.
Идентификаторы заданий:
- group-reminder-<service_id>-<reminder_id> — групповые;
- user-reminder-<actor_id>-schedule-<schedule_id> — персональные.

При старте бота:
- удаляются все job'ы с префиксом service-reminder-* (legacy);
- создаются job'ы group-reminder-* по текущим group_reminders с
  enabled = 1;
- создаются job'ы user-reminder-* по текущим активным расписаниям.

Обработка перезапуска: при старте читаются все активные расписания и
пересоздаются job'ы. Неуспешные доставки повторяются при следующем
запуске. Переход через полночь, месяц, год сохраняет правильную
целевую дату (см. scheduled_reminder_date).

4.6. Асинхронность и отмена

Задания планировщика выполняются асинхронно. Каждое защищено
asyncio.Lock по ключу (service_id, event_date) для групповых и
(actor_id, event_date) для персональных. Это исключает параллельные
отправки одного и того же уведомления.

При graceful shutdown приложение ожидает завершения активных заданий
не более 30 секунд, затем отменяет их.


5. БЕЗОПАСНОСТЬ И УСТОЙЧИВОСТЬ К СБОЯМ

Retry при скачивании расписания — до 3 попыток с интервалом 5 минут.
При полной неудаче — алерт администратору, рассылка не выполняется.

Часовой пояс — принудительно из credentials во всех операциях сравнения
дат и в планировщике.

Самоочистка кэша — в /dev/shm хранится только текущая неделя. При
парсинге новой даты старый state cache затирается.

Graceful shutdown — после SIGTERM/SIGINT планировщик приостанавливает
новые задания, приложение ожидает текущую рассылку не более 30 секунд,
затем закрывает сессию aiogram. При превышении таймаута активная задача
отменяется. manage.sh stop ожидает до 35 секунд до принудительного
завершения. reminder_bot_bot.pid удаляется перед выходом.

Защита от запуска второй копии — эксклюзивная блокировка в SHM_DIR
(application_instance_lock). И запуск бота, и restore-data используют
её; начать одну операцию во время другой нельзя.

Права на файлы — логи и бэкапы 600, каталоги 700. PID-файл создаётся
атомарно с правами 600 и удаляется только владельцем.


6. УПРАВЛЕНИЕ СКРИПТОМ (manage.sh) И АВТОЗАПУСК (cron)

В корне проекта — bash-скрипт manage.sh. Симлинк reminder_bot_manage.sh
указывает на него для совместимости с ТЗ.

Окружение (test или prod) определяется по имени каталога, в котором
лежит скрипт. Запускать команды следует из каталога развёртывания, не
из src/.

6.1. Команды

start — проверяет reminder_bot_bot.pid. Если процесс не запущен —
активирует venv, восстанавливает reminder_bot_interaction.log из
последнего бэкапа (если ОЗУ чистая), запускает бота через nohup,
сохраняет PID + starttime. Если процесс работает — выход с кодом 1
(идемпотентность для cron).

stop — делает backup, мягко тушит процесс через kill -15, при
необходимости — kill -9, удаляет PID-файл. Дополнительно находит и
останавливает legacy-процессы reminder_bot.py без PID-файла.

restart — stop, затем start.

status — печатает БОТ РАБОТАЕТ / БОТ ОСТАНОВЛЕН (первая строка stdout)
для CI-проверок.

backup — копирует reminder_bot_interaction.log из ОЗУ на диск в
logs_backup/ с датой в имени.

backup-data — создаёт проверенный снимок SQLite, SQL-экспорта, кэша,
XLSX и нормализованного JSON на внешнем диске (раздел 4 tz2.txt).

restore-data <snapshot> — проверяет снимок и восстанавливает данные.
Только при остановленном боте, только для того же окружения.

logs / debug-logs / clear-logs — просмотр и очистка reminder_bot_*.log,
sys_nohup.log. Поддерживают --follow.

webapp start|stop|restart|status — управление HTTP-сервером Web App.
PID в --shm-dir/reminder_bot_webapp.pid, журнал в
--log-dir/reminder_bot_webapp.log.

6.2. Передаваемые боту аргументы

┌─────────────────────┬────────────┬──────────────────────────────┬─────────────────────────────────────────────┐
│ Аргумент            │ Обязателен │ Значение по умолчанию        │ Назначение                                  │
├─────────────────────┼────────────┼──────────────────────────────┼─────────────────────────────────────────────┤
│ --shm-dir <path>    │ да         │ /dev/shm/reminder_bot/<env>  │ PID, xlsx, state_cache, webapp.pid          │
│ --log-dir <path>    │ да         │ равно --shm-dir              │ interaction.log, debug.log, nohup.log       │
└─────────────────────┴────────────┴──────────────────────────────┴─────────────────────────────────────────────┘

Переопределение через переменные окружения:

    SHM_DIR=/dev/shm/reminder_bot/prod LOG_DIR=/var/log/reminder_bot ./manage.sh start

<env> определяется автоматически как имя каталога manage.sh.

6.3. Контракт с reminder_bot.py

1. Разбор аргументов через argparse: --shm-dir, --log-dir.
2. --shm-dir — PID, xlsx, state_cache, webapp.pid.
3. --log-dir — interaction.log, debug.log, nohup.log, webapp.log.
4. Создавать обе директории при старте.
5. Удалять reminder_bot_bot.pid при graceful shutdown.

7. СЦЕНАРИЙ CI/CD ПАЙПЛАЙНА

Автоматический деплой — .github/workflows/deploy.yml, self-hosted
runner с меткой tunmonitor.

7.1. Ветки

dev — рабочая ветка разработки.
test — тестовая ветка, из неё развёртывается /mnt/external_data/reminder_bot/test.
main — боевая ветка, из неё развёртывается /home/pi/app/reminder_bot/prod.

7.2. Триггеры

pull_request в test или main.
push в main.

7.3. Job'ы

unit-tests — на ubuntu-latest, Python 3.12, запускает python -m
unittest discover -s tests -v или pytest.

deploy:
- runs-on [self-hosted, tunmonitor];
- concurrency group, cancel-in-progress: false — защита от
  параллельных деплоев в одно окружение;
- для PR dev→test: TARGET_DIR=/mnt/external_data/reminder_bot/test,
  SHM_DIR=/dev/shm/reminder_bot/test;
- для push в main: TARGET_DIR=/home/pi/app/reminder_bot/prod,
  SHM_DIR=/dev/shm/reminder_bot/prod.

7.4. Порядок шагов в deploy

1. checkout проверяемого коммита.
2. rsync с исключениями: .git/, credentials.env, templates.json,
   schedule_config.json, webapp_config.json, logs_backup/, venv/,
   .venv/, __pycache__/, *.log, qodo_review.md.
3. Проверка hash requirements.txt — пропуск pip install, если не
   менялся.
4. manage.sh stop.
5. manage.sh start с env RUNNER_TRACKING_ID=0.
6. sleep 4, manage.sh status. Проверка «БОТ РАБОТАЕТ».
7. Fallback: если job упал после остановки бота — попытка перезапуска
   через trap EXIT.

7.5. Ограничения

Runtime-логи не выгружаются в GitHub artifacts.
Секреты (credentials, токены, шаблоны) сохраняются в папках окружений
и не синхронизируются.

7.6. Управление секретами

Секрет PAT_TUNMONITOR не требуется для публичного репозитория. При
переводе в приватный — создать в Settings → Secrets → Actions и
передавать через actions/checkout с persist-credentials: false.


8. СТРУКТУРА ШАБЛОНОВ И ФАЙЛОВ КОНФИГУРАЦИИ

8.1. reminder_bot_templates.json — общие шаблоны ролей

Файл используется только как источник шаблонов для legacy-сценариев
и общий fallback. Для новых служений тексты настраиваются
администратором через /service_notify и хранятся в SQLite:

- services.group_template — шаблон по умолчанию для групповых
  напоминаний, у которых body = NULL;
- services.personal_templates_json — словарь шаблонов по задачам;
- group_reminders.body — индивидуальные тексты групповых напоминаний
  (могут быть NULL).

Файл reminder_bot_templates.json:

{
  "general": "📋 Напоминание о служении на предстоящее воскресенье
({sunday_date}):\n\n{task_assignments}",
  "roles": {
    "Ответственный": "Приветствуем, {name}! Вы назначены ролью
[Ответственный] на {sunday_date}. Подтвердите участие.",
    "Ведущий": "Привет, {name}! В это воскресенье ({sunday_date}) ты
[Ведущий]. Подтверди кнопкой ниже.",
    "Проповедник": "Здравствуйте, {name}. Напоминаем о вашей проповеди
({sunday_date})."
  }
}

8.2. Поля группового шаблона

services.group_template — fallback-шаблон служения для всех записей
group_reminders с body = NULL. При отсутствии пользовательского
fallback применяется встроенный DEFAULT_GROUP_TEMPLATE. Собственный
body напоминания всегда имеет приоритет над обоими шаблонами.

Допустимые поля для services.group_template и group_reminders.body:
- {service_name} — название служения;
- {sunday_date} — дата воскресенья в формате ДД.ММ.ГГГГ;
- {task_assignments} — список задач и ответственных, сгруппированный
  по задачам.

Поле {task_assignments} заменяется текстом вида:

    микрофон 🎤
    Аркадий (@arkady)
    Евгений (@evgen)

    проповедь 📖
    Денис (@denis)

Информационные задачи (помеченные в Excel как `* ...` или `[...]`)
в {task_assignments} не подставляются.

Поля вида {tg_responsible}, {tg_leader}, {tg_preacher} НЕ являются
допустимыми для нового формата. При попытке сохранить шаблон с
неизвестным полем — ошибка с указанием допустимых.

8.3. Поля личного шаблона

Допустимые поля для services.personal_templates_json и
user_reminder_texts.body:
- {name} — имя участника;
- {task} — название задачи;
- {service_name} — название служения;
- {sunday_date} — дата воскресенья;
- {telegram_id} — Telegram ID участника;
- {username} — username участника без @.

8.4. webapp_config.json — настройки Web App

Файл создаётся в каждом окружении (test / prod) и исключён из Git.

{
  "host": "127.0.0.1",
  "port": 8080,
  "public_url": "https://app.example.com/webapp/"
}

Поля:
- host — адрес привязки HTTP-сервера. По умолчанию 127.0.0.1.
- port — целое число 1–65535. Test и prod используют разные порты.
- public_url — HTTPS URL страницы Web App после настройки reverse
  proxy. Используется ботом для регистрации кнопки меню Telegram.

Если public_url не задан, HTTP-сервер работает, но кнопка меню не
регистрируется.

8.5. reminder_bot_credentials.env — конфиденциальные настройки

BOT_TOKEN=...
ADMIN_TG_ID=...
GROUP_CHAT_ID=...
YANDEX_PUBLIC_URL=...
TIMEZONE=Europe/Moscow
REMINDER_BOT_DB_PATH=.runtime/reminder_bot.sqlite3

Все поля обязательны, кроме REMINDER_BOT_DB_PATH (значение по
умолчанию указано выше).

8.6. Пример group_reminders в БД

Для служения «assembly» после миграции и настройки:

    id  service_id  body                                    reminder_days  reminder_time  enabled
    1   assembly    NULL                                    3              18:00          1
    2   assembly    "Напоминаем: завтра служба!"            1              09:00          1
    3   assembly    NULL                                    0              07:00          1

Напоминание 1 использует services.group_template.
Напоминание 2 использует собственный текст.
