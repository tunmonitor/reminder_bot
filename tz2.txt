РАЗДЕЛ 2. ФОРМАТ EXCEL И ПОВЕДЕНИЕ ПАРСЕРА
(дополнение к разделу 2 основного zt.txt)

2.0. Получение и открытие файла

Перед сеансом бот получает опубликованный xlsx с Яндекс.Диска. Скачанный
рабочий файл хранится в --shm-dir/reminder_bot_current.xlsx. Утилита проверки
python -m bot.debug_schedule скачивает отдельную копию в отдельный каталог
внутри /dev/shm/reminder_bot/debug/ и выполняет только локальную
проверку/имитацию: сообщения ни в Telegram-группу, ни адресатам не
отправляются. Скачанный файл и логи в debug-каталоге не удаляются
автоматически; временные копии, созданные только для одного тестового
запуска, должны удаляться при его завершении.

Утилита отладки пишет:
- полученные роли, имена и найденные Telegram-данные;
- ошибки и пропущенные данные;
- полностью подготовленный групповой текст;
- подготовленный текст каждого личного сообщения для найденного адресата.

2.1. Лист месячного расписания

Имя листа составляется из русского названия месяца и двух цифр года, например
«ОКТЯБРЬ26». Поиск листа не зависит от регистра. Для даты 11 октября 2026 года
обрабатывается лист «ОКТЯБРЬ26».

Первая строка может содержать название служения, например «СОБРАНИЕ».
Строки дат в колонке A открывают отдельные блоки. Дата может быть записана
как дата Excel, «11 октября», «11 октября 2026» или ДД.ММ.ГГГГ. Если в
текстовой дате нет года, год берётся из целевой даты. Блок заканчивается при
встрече следующей даты; пустая строка его не закрывает.

В строках блока задача находится в A, назначенное имя — в B. Порядок задач
произвольный; названия распознаются без учёта регистра:
- «ХКЦ» → роль «Ответственный»;
- «Ведущий» и «Ведет» → роль «Ведущий»;
- «Проповедует» и «Проповедет» → роль «Проповедник».

2.2. Лист «Списки»

Заголовок блока задачи находится в A и может встретиться на любой строке,
не только в первой. В строках участников имя записано в A, username в B,
Telegram ID в C. Следующий заголовок задачи начинает следующий блок.
Поддерживаемые заголовки — ХКЦ, Ведущий/Ведет, Проповедует/Проповедет;
регистр не важен.

Список может содержать незаполненные и частично заполненные строки. Для
рассылки каждому назначенному человеку нужен положительный целый Telegram ID.
Username необязателен. Если назначенное имя отсутствует в блоке или у записи
не заполнен/не распознан ID, это отмечается как проблема конкретной роли;
остальные корректные назначения продолжают использоваться.

2.3. Особенности формата xlsx

Парсер сбрасывает ошибочное объявление диапазона листа, например A1 при
наличии данных на последующих строках, и читает фактические ячейки.
Если stylesheet содержит недопустимое для openpyxl значение стиля границы
«solid», парсер создаёт временную in-memory копию xlsx с нормализованным
стилем «thin». Исходный скачанный файл не изменяется.

2.4. Ошибки и неполные данные

Если невозможно скачать/прочитать книгу, не найден месячный лист или дата,
соответствующая ошибка записывается в debug-лог и администратору отправляется
сообщение в Telegram. Для ошибки данных отдельной роли (нет назначения, имя
не найдено в её блоке либо отсутствует корректный Telegram ID) бот сообщает
администратору, но не отменяет всю рассылку.

Групповое сообщение отправляется и при неполном наборе ролей. Для отсутствующей
групповой отметки используется текст «не найден»; для найденного username
используется @username. Личные сообщения с кнопкой подтверждения отправляются
только участникам с корректным Telegram ID. Кэш участников содержит только
фактически разрешённые назначения.

Перед реальной рассылкой отладочный режим позволяет проверить всё без
взаимодействия с Telegram:

    /home/pi/.venv/bin/python -m bot.debug_schedule --date 2026-10-11

Итоговые подготовленные тексты находятся в
/dev/shm/reminder_bot/debug/reminder_bot_debug.log. Каталог закрыт правами 700,
файлы — 600. Данные Telegram в логах конфиденциальны.

3. ФОРМАТИРОВАНИЕ И ВИЗУАЛИЗАЦИЯ ДИАЛОГОВ

Требования этого раздела применяются ко всем пользовательским поверхностям
бота: сообщениям и кнопкам в личных чатах, административным командам,
пошаговым настройкам, callback-ответам, персональным напоминаниям и
уведомлениям в группах. Новый диалог или экран должен продолжать общий стиль,
не меняя существующие права доступа, callback-маршруты и смысл действий.

3.1. Структура сообщения

- Начинать экран с короткого заголовка, из которого понятно, какой объект
  открыт (например, «⚙️ СОБРАНИЕ»); уместный статус показывать рядом с ним.
- Связанные значения собирать в смысловые блоки с короткими заголовками:
  основные настройки, администраторы, ответственные, уведомления.
- Длинные однотипные перечни группировать по роли или задаче, не повторять
  название роли в каждой записи, если её можно вынести в заголовок группы.
- Оставлять пустую строку между блоками. Не превращать экран в сплошной
  абзац, но и не добавлять пустые строки между каждой однотипной записью.
- Показывать важные текущие значения и следующий шаг; длинную инструкцию,
  повторяющую назначение кнопки, заменять одной короткой подсказкой.
- Не скрывать за компактным резюме данные или действия, нужные для выполнения
  текущего сценария. Если подробностей слишком много, применять пагинацию
  или последовательный выбор.

Пример карточки настроек:

    ⚙️ СОБРАНИЕ · статус: 🟢 включено

    📡 Настройки
    ├ Групповой чат: -1003714349429
    ├ Напоминание: за 1 дн. в 18:00
    ├ Текст для группы: ⚪ не задан
    └ Личные шаблоны: ⚪ не заданы

    👤 Администраторы
    └ 181601986 · @albazrov

    👥 Ответственные
    ├ Ведущие: Аркадий (ID 718343838), Евгений (ID 306139797)
    └ Проповедники: Денис (ID 801625873)

    ℹ️ Чтобы изменить параметры, нажмите кнопку ниже.

3.2. Значки и статусы

Использовать значки последовательно и только там, где они ускоряют понимание:

- ✅ — действие выполнено или настройка сохранена;
- ❌ — действие не выполнено из-за ошибки;
- ⚠️ — действие выполнено частично или есть ограничение/предупреждение;
- ℹ️ — нейтральная подсказка или пояснение;
- ⏳ — выполняется загрузка или другая длительная операция;
- 🟢 / 🔴 — включённое / выключенное состояние;
- ⚪ — значение не задано или список пуст;
- ⚙️ — карточка настройки; 📡 — групповой чат; 👤 / 👥 — человек /
  участники; 🔔 — напоминания; 📝 — тексты; 📅 / 🕒 — дата или срок /
  время; ⬅️ — возврат.

Не заменять текстовый статус одним цветным кружком, если само состояние
неочевидно. Для пустого значения писать «⚪ не задано/не заданы», а не
показывать его как ошибку. Не добавлять дублирующие эмодзи в каждую строку
одного блока.

3.3. Сообщения и действия

- Успех формулировать кратко: «✅ Настройки сохранены · СОБРАНИЕ».
- Ошибку сопровождать понятным следующим действием, если оно известно:
  «❌ Служение не найдено · обновите список командой /service_settings».
- Предупреждение не должно создавать впечатление полного успеха:
  «⚠️ Чат не привязан · групповые напоминания не отправляются».
- Приглашение к вводу должно однозначно описывать ожидаемый формат:
  «ℹ️ Введите время в формате ЧЧ:ММ (например, 18:00)».
- Длительную работу обозначать как выполняющуюся; сообщение об успехе
  отправлять только после фактического завершения операции.
- Текст кнопки должен описывать действие, а не техническое имя callback.
  Кнопки «назад», «отмена», «сохранить» должны различаться по назначению и
  вести в прежнюю точку сценария.
- Не менять callback_data, проверку прав, последовательность подтверждений
  или доступность действий только ради оформления.
- Callback-ответы короткие, без HTML, с теми же маркерами статуса; учитывать
  ограничение Telegram на длину callback-ответа.

3.4. Персональные и групповые уведомления

- Персональное напоминание начинается с короткого маркера 🔔 и сохраняет
  персональное обращение, роль, дату и кнопку подтверждения, если она
  предусмотрена сценарием.
- Успешное подтверждение обозначается ✅ в сообщении участника и в тексте
  результата; повторное подтверждение обозначается ℹ️ и не должно выглядеть
  как новое действие.
- Если подтверждение сохранено, но уведомление в группу не доставлено,
  отображать ⚠️ и явно указывать, что именно не выполнено.
- Сообщение группы должно оставаться понятным без административного
  контекста; не включать в него секреты, внутренние пути и лишние Telegram ID.
- Не менять смысл, состав адресатов, доступность или пользовательские
  placeholder-поля шаблонов ради добавления визуальных маркеров.

3.5. Безопасность и ограничения Telegram

- Текущие сообщения отправляются с parse_mode=None. Сохранять этот режим,
  если форматирование HTML/Markdown не является необходимым для задачи.
  Если parse mode вводится намеренно, все пользовательские значения
  (имена, задачи, username, тексты, ссылки и ошибки внешних систем) должны
  экранироваться библиотекой aiogram до вставки в разметку.
- Telegram ID и chat ID показывать как значения без изменения знака и цифр;
  при необходимости копирования допускается выделять их через поддерживаемую
  безопасную разметку только при включённом соответствующем parse mode.
- Показывать username только когда он присутствует в данных; не
  конструировать username из имени и не изменять регистр/содержимое.
- Проверять длину сообщения по лимиту Telegram в UTF-16 code units
  (максимум 4096 для обычного текстового сообщения). Длинные списки
  разбивать на безопасные части, прикрепляя клавиатуру к последней части.
- Соблюдать лимиты Telegram на callback_data (не более 64 байт UTF-8),
  callback-ответы и число кнопок; на телефоне избегать перегруженных рядов,
  по возможности размещать не более трёх кнопок в строке.
- Не считать эмодзи или визуальную группировку заменой валидации данных,
  обработки ошибок, проверок доступа или журналирования.

3.6. Проверка нового оформления

- Проверить сформированный текст для пустых, частично заполненных и полных
  данных, а также для выключенного служения и отсутствующего группового чата.
- Проверить, что имена задач/пользователей с Unicode и специальными
  символами не ломают сообщение или HTML-разметку.
- Проверить сохранность callback_data, порядка кнопок и переходов сценария;
  тесты должны утверждать необходимые действия и их callback_data, а не
  зависеть от декоративного эмодзи, если он не является предметом теста.
- Проверить лимит Telegram на сообщениях с длинными списками.
- Проверить напоминание, успешное/повторное подтверждение и сценарий
  частичной ошибки доставки без отправки тестовых сообщений реальным людям.

4. РЕЗЕРВНОЕ КОПИРОВАНИЕ И ВОССТАНОВЛЕНИЕ

Правила размещения, триггеры, права доступа и обработка недоступности диска
определены в разделе 1.6 основного zt.txt. Этот раздел задаёт состав и
проверяемый формат резервного набора. Резервирование данных приложения
отличается от команды backup в разделе 6 основного ТЗ: эта команда сохраняет
только журналы взаимодействий.

4.1. Состав согласованного снимка

Каждый снимок относится к одному окружению (test или prod) и содержит:

- `database.sqlite3` — согласованную копию SQLite-базы, пригодную для
  непосредственного восстановления;
- `database.sql` — текстовый SQL-экспорт той же базы для просмотра и
  выборочного импорта; он не заменяет SQLite-копию;
- `reminder_state_cache.json` — состояние подтверждений и текущей рассылки,
  если файл существует на момент снимка;
- `schedule.xlsx` — исходную книгу расписания, без нормализации или иных
  изменений;
- `schedule.json` — нормализованные распознанные данные из XLSX для быстрого
  восстановления и проверки результата парсинга;
- `manifest.json` — метаданные и контрольные суммы всех файлов набора,
  исключая сам manifest.

SQLite копировать согласованным механизмом SQLite (online backup API либо
эквивалентным безопасным способом), а не обычным копированием открытого файла.
SQL-экспорт формировать из того же логического состояния базы. В `schedule.json`
включать версию формата, дату и время обработки, хеш исходного XLSX,
обработанный месяц/год, распознанные служения и назначения (роль и имя), а
также распознанные контакты (роль, имя, username при наличии и Telegram ID).
Даты хранить в ISO 8601. Нормализованный JSON не считать заменой SQLite или
оригинального XLSX.

Не включать в снимок `credentials.env`, токены, пароли, логи, временные файлы
или посторонние файлы. Снимок может содержать персональные данные и Telegram
ID, поэтому обязательны права доступа из раздела 1.6; не выводить содержимое
снимка в логи.

4.2. Именование, целостность и публикация

Каждый законченный набор сохранять в отдельном каталоге с временной меткой
создания в настроенном часовом поясе, например:

    /mnt/external_data/reminder_bot/backups/prod/2026-10-11T03-00-00/

Формат метки должен быть безопасен для имени каталога и однозначно обозначать
время; при совпадении имён добавлять уникальный суффикс. `manifest.json`
должен содержать идентификатор окружения, время создания, версию схемы/формата,
относительное имя, размер в байтах и SHA-256 каждого файла. До публикации
набора проверить читаемость файлов, контрольные суммы и выполнить
`PRAGMA integrity_check` для SQLite-копии. Временные компоненты создавать
только внутри каталога резервных копий на смонтированном внешнем диске.
Сначала записать и проверить весь набор, затем атомарно опубликовать его;
неполный или непроверенный набор не считается резервной копией и не должен
выбираться для восстановления.

Успех резервирования подтверждать только после публикации и проверки полного
набора. При ошибке явно записать причину и уведомить администратора; не
создавать успешный manifest для неполного набора и не переключаться на другое
хранилище. Ошибка резервирования сама по себе не должна приводить к отправке
ложного уведомления об успехе или к потере доступных рабочих данных.

Снимки с временными метками не удалять автоматически. Любое введение срока
хранения или очистки старых снимков требует отдельного требования и проверки,
что остаётся пригодный полный снимок каждого окружения.

4.3. Восстановление

Для восстановления выбирать последний полный снимок, у которого успешно
проверены manifest, хеши всех файлов и целостность SQLite. Проверять, что
идентификатор окружения совпадает с целевым; восстановление test-снимка в prod
и наоборот запрещено без отдельной явной процедуры миграции.

SQLite восстанавливать из `database.sqlite3`; `database.sql` служит
альтернативой для ручного экспорта/импорта, но не имеет приоритета над
проверенной SQLite-копией. Исходный XLSX восстанавливать из `schedule.xlsx`,
а `schedule.json` использовать для быстрого восстановления распознанного
представления только при совпадении его хеша источника с XLSX. Кэш состояния
восстанавливать только если он присутствует и прошёл проверку формата.
Проверить все компоненты до замены рабочих файлов; не перезаписывать
действующие данные частично. После восстановления проверить запуск приложения,
чтение базы и расписания и зафиксировать результат в журнале без записи
содержимого базы или пользовательских данных.

В production восстановление выполнять командой
`manage.sh restore-data <snapshot-directory>` после остановки бота; если рядом
с SQLite остались файлы `-wal`/`-shm`, сначала разобраться с их состоянием,
автоматически удалять их нельзя. Для атомарной установки короткоживущие
восстановительные staging-файлы создаются рядом с целевыми файлами, имеют
права 600 и удаляются после успеха или отката. Это узкое исключение только для
процедуры восстановления; временные файлы тестирования по-прежнему размещаются
только в заданном каталоге `/dev/shm`.

4.4. Запуск и диагностика бэкапа

- При старте экземпляра выполнить снимок; если рабочей копии XLSX ещё нет,
  один раз скачать файл с Яндекс.Диска в `--shm-dir` без отправки сообщений.
  При неудаче явно сообщить администратору и продолжить штатный запуск бота.
- В работающем экземпляре планировать ежедневный снимок на 03:00 в timezone
  из credentials и debounce-снимок через 10 минут тишины после изменений
  SQLite, state cache или скачанного XLSX. Новое изменение сбрасывает таймер.
- Изменения SQLite и кэша обнаруживать в точках сохранения данных, а не
  опрашиванием всего диска. Новая версия загруженного XLSX определяется по
  изменению SHA-256.
- `manage.sh backup-data` запускает ручной снимок. Существующая команда
  `manage.sh backup` остаётся только для interaction.log.
- При недоступном диске, невалидном исходном файле или ошибке проверки
  снимок не публиковать как успешный; записать причину и уведомить
  администратора. Не удалять старые копии автоматически.

5. TELEGRAM WEB APP (MINI APP)

Расположение, конфигурация и совместный запуск HTTP-сервиса с ботом заданы в
разделе 1.7 основного zt.txt. Существующий `webapp/index.html` — начальная
страница проекта, а не законченный интерфейс; при реализации сохранять этот
путь и использовать Telegram Web Apps JavaScript API для интеграции с клиентом
Telegram.

5.1. Раздача и конфигурация

- Статические файлы Web App размещать только в `webapp/`; корнем HTTP-сервера
  задавать этот каталог, не корень проекта. Запросы с `..`, абсолютными
  путями, symlink-выходом за пределы корня и неизвестными файлами не должны
  давать доступ к конфигурации, коду бота, базе или runtime-данным.
- Для лёгкой раздачи статических файлов допускается стандартный модуль Python
  `http.server`; не добавлять веб-фреймворк или зависимости без необходимости.
- Настройки каждого окружения хранить в исключённом из Git
  `webapp_config.json`. Как минимум задать `host` и `port`; порт обязателен,
  должен быть целым числом в диапазоне 1–65535 и проверяться при запуске.
  Для отсутствующего файла или некорректного значения сообщать понятную
  ошибку, а не молча подставлять другой порт. Пример тестовой настройки:
  `{"host":"127.0.0.1","port":8080}`.
- Test и prod должны использовать отдельные конфиги и не конфликтовать по
  порту. Каждый экземпляр сервиса управляется отдельно от бота командой
  `manage.sh webapp start|stop|restart|status`; процесс бота не должен
  неявно запускать или останавливать Web App. Сервис должен сообщать о
  занятости порта или иных ошибках запуска.
- Публичная точка входа Telegram Web App обязана использовать HTTPS. При
  использовании стандартного HTTP-сервера его слушать локально и размещать
  за HTTPS reverse proxy; не считать доступный из Интернета открытый HTTP
  сервер допустимым вариантом.

5.2. Telegram и безопасность

- Браузерный клиент передаёт `Telegram.WebApp.initData` серверу только по
  HTTPS. Любые доверенные действия и персональные данные проверять по
  криптографически валидированному `initData` на серверной стороне с токеном
  бота; токен никогда не передавать в браузер.
- `initDataUnsafe` допускается только для предварительного отображения
  интерфейса и не является доказательством личности или полномочий.
  Проверять срок актуальности `auth_date`, идентификатор пользователя и
  требуемые права для каждой защищённой операции.
- Не помещать секреты, персональные данные или токены в клиентские файлы,
  URL-параметры, диагностические сообщения или логи. Не включать в ответ
  больше пользовательских/служебных данных, чем необходимо интерфейсу.
- Встроенный сервер статических файлов не должен сам по себе становиться
  незащищённым API. Если Mini App требует операций с данными бота, такие
  операции реализовать отдельными явно ограниченными обработчиками с
  аутентификацией, проверкой полномочий и валидацией входных данных.

5.3. Проверка и приёмка

- Проверить раздачу `webapp/index.html` и нужных ресурсов, MIME-типы,
  корректный путь к корню, отказ в доступе к файлам за пределами `webapp/`,
  а также поведение для отсутствующих файлов.
- Проверить чтение host/port из конфигурации, некорректный/занятый порт,
  одновременные отдельные test/prod экземпляры, команды `manage.sh webapp
  start|stop|restart|status` и корректную остановку сервера.
- Проверить Telegram-клиентский сценарий в тестовом окружении без отправки
  сообщений реальным пользователям. Проверка серверной аутентификации должна
  включать валидный, поддельный, просроченный и отсутствующий `initData`;
  недействительные данные не должны давать доступ к защищённым операциям.
- Проверить, что публичная ссылка работает по HTTPS через конфигурацию
  reverse proxy, а секреты не попадают в браузерную сборку и логи.
